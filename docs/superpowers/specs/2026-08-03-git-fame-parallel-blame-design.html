Parallel git blame inside a single repository

Context render-impact.py shells out to git fame once per external repository to count surviving lines. Measurement showed git-fame spends 41% of its wall time on process spawn alone, because it runs one serial git blame subprocess per file. This spec decides to fix the dependency rather than work around it: patch git-fame in a fork, upstream the patch, and pin the patched build.

Decision
Add a -j/--jobs option to git-fame that parallelises the per-file blame subprocess, on by default, and consume it from a pinned fork build.
Chosen over working around it in render-impact.py because the cost lives entirely inside the dependency — a caller-side fix (parallelising the repo loop) would leave the per-file serialisation in place for every other git-fame user and would oversubscribe the box once the real fix landed. Upstream already parallelises across repositories with thread_map (_gitfame.py:441), so intra-repo parallelism is consistent with the project's own precedent, not a novel behaviour.
The decision deliberately does not change any output. Only the subprocess call is parallelised; parsing and aggregation stay serial in the main thread, consuming results in submission order, so output is byte-identical to -j1.

Background — the measurement

Every number below was measured on this box (12 cores), not estimated.

git-fame spawns N + 3 processes per repository, where N is the number of text files: ls-files, git grep -I, shortlog, then one git blame --line-porcelain per file, strictly serially (_gitfame.py:280).

The fixed per-call cost is ~5.4 ms, and it is not an artifact of the estimate: blaming a 0-byte file costs 5.44 ms against a 4.10 ms bare git rev-parse. Median blame in that repo is ~10 ms, so roughly half of every blame call is fork/exec/repo-open rather than blame work.

Thread-pooling the same 477 blames confirms the headroom. The prediction before running was 1.0–1.6 s at 8 workers; it came in at 1.615 s.

Extrapolating the measured ~70 loc/file across the 56 cached repositories (5.95 M lines) puts a --resync at ~85,000 blame processes, ~7.5 min of pure fork/exec before any blaming happens.

02

Approach chosen vs. rejected

Three approaches were considered; the caller-side workarounds were rejected.

Rejected — caller-side only
  • Thread-pool the repo loop in blame_moved — helps only when several repos move in one run, and does nothing for a single large repo.
  • Leaves per-file serialisation in place for every other git-fame user; the upstream bug goes unreported.
  • Oversubscribes the box if the real fix later lands upstream.
  • Swapping git-fame for another blame aggregator changes semantics with no failing test to say what moved.
Chosen — fix the dependency
  • Patch git-fame itself; the win applies to every caller and every repo size.
  • Fork to Nitjsefnie-OSC, open an upstream issue and send the PR, so the fix is not carried privately forever.
  • Pin the patched build and add a regression test that fails on the stock version.
  • Output is byte-identical, so the change is provable rather than merely plausible.
03

Change inventory

Upstream fork first, consumer second.

gitfame/_gitfame.py (module docstring)
Declare the option. argopt builds the parser from __doc__, so the docstring is the source of truth: -j, --jobs=<n> with [default: 0:int], 0 meaning auto.
gitfame/_gitfame.py:_get_auth_stats
Parallelise the blame subprocess. Accept a jobs parameter. Submit blame calls to a ThreadPoolExecutor with a bounded window of 2 × jobs outstanding futures; consume in submission order and parse serially in the calling thread, so stats_append needs no lock and output order is unchanged. Per-file exception handling keeps its current semantics (log, skip file).
gitfame/_gitfame.py:run
Resolve and divide the budget. jobs=0 resolves to min(32, (os.cpu_count() or 1) + 4) — the stdlib ThreadPoolExecutor heuristic, easy to defend in review. When multiple gitdirs are processed concurrently, pass max(1, jobs // len(gitdirs)) inward so total concurrency stays bounded.
tests/test_gitfame.py
Cover the flag and the invariant. Add ['-j', '4'] to the test_options parametrize list, plus a determinism test asserting -j1 and -j4 produce identical output on the repo itself.
git-fame_completion.bash
Offer the new flag. Add -j / --jobs to the completion word list.
gitfame/git-fame.1
Regenerate. Produced by the Makefile target from the docstring; must be rebuilt so the man page matches.
/root/gh-widgets/test_impact.py (new)
Regression test that fails on stock. Capability probe: assert the installed git-fame accepts -j, and that -j4 output equals -j1 output. No timing assertion — those are flaky.
/root/gh-widgets/CLAUDE.md + install.sh
Record the pin. Note that git-fame is installed from Nitjsefnie-OSC/git-fame at a fixed commit, why, and how to re-pin once the upstream PR merges.
04

Concurrency semantics

Exactly what each value of --jobs does.

ValueBlame workersBehaviour
0 (default)min(32, cpu_count+4)Auto. Matches the stdlib executor heuristic.
11Exactly the current serial code path — the escape hatch, and the determinism test's control.
n > 1nExplicit cap.
multiple gitdirsmax(1, jobs // len(gitdirs))Outer thread_map already parallelises across repos; inner budget is divided so the product stays bounded.

Memory is the constraint that forces the bounded window rather than a plain executor.map: --line-porcelain emits roughly 250–400 bytes per source line, so buffering every file's blame output at once would reach gigabytes on a 1.3 M-line repository like packit/ogr. Peak memory stays O(jobs × per-file output), not O(repo).

05

Verification

Concrete and runnable. The first item is the one that makes the change provable.

Byte-identical output. git fame -e -w --format json -j1 and -j8 produce identical JSON on at least three real repositories of differing size.
Upstream suite green. pytest in the fork passes, including -W=error and --cov-fail-under=85.
Speedup reproduced. -j8 beats -j1 by ≥3× on the 477-file repo; recorded, not asserted in a test.
Regression test fails on stock. The new gh-widgets test passes against the pinned fork build and fails against git-fame 3.1.2 from PyPI.
End-to-end unchanged. render-impact.py against a copied cache produces the same ourloc counts as the current production cache for repos whose HEAD has not moved.
Deployed copies match. diff /usr/local/bin/render-impact.py /root/gh-widgets/render-impact.py is empty after install.sh.

Risks

Mitigation
Memory blow-up on very large repos if the outstanding-future window is unbounded.
MED
Bounded window of 2 × jobs is a hard requirement of the design, not an optimisation. Verified against a large repo before the PR.
Upstream rejects default-on parallelism as a behaviour change.
LOW
Byte-identical output plus the existing thread_map precedent is the argument. If rejected, flip the default to -j1 and pass -j explicitly from render-impact.py — a one-line change on our side.

LOW

Pinning to a fork commit drifts from upstream releases.

07

Out of scope

Considered and deliberately deferred.

Parallelising blame_moved in render-impact.py
Deferred until the git-fame fix is deployed and measured. Doing both would oversubscribe a 12-core box. Revisit only if runs with many moved repos are still slow afterwards.
Replacing per-file blame with a single git log pass
Would remove the N-process structure entirely, but changes what "surviving lines" means and is a far larger upstream argument. Out of scope for a performance patch.
