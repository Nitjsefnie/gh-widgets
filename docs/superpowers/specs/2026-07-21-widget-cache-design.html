Design spec · gh-widgets

Cache what is genuinely immutable, refetch everything else

Context render.py is stateless: every hourly run refetches a full year of contribution calendar, every authored PR, and every authored issue. GitHub now rejects the calendar query with RESOURCE_LIMITS_EXCEEDED on most runs — 5 of 6 runs failed on 2026-07-21 — so the profile widgets survive on intermittent luck. This spec replaces the stateless fetch with an incremental cache, keyed on real immutability rather than age alone.

Decision
Persist a JSON cache; treat only settled calendar days and MERGED PRs as immutable; refetch everything mutable each run.
Two layers, deliberately ordered. Durability: a successful fetch is written to a cache file, and a failed fetch renders from that cache instead of exiting non-zero — the widgets stop breaking immediately, whatever GitHub's limiter does. Reduction: the calendar is fetched as a trailing 7-day window merged onto cached history, and PRs are split so that the 192 MERGED ones are never refetched.
The cutoff is state, not age, everywhere except the calendar. CLOSED is explicitly not treated as settled: a closed PR can be reopened and later merged, and the GraphQL schema's IssueStateReason enum contains REOPENED, so the issue analog is reopenable too. An age-based cutoff would silently undercount the late merges that make up most of this profile's contributions.
01

Background — the observed failure

Evidence from the box, not inference.

journalctl -u render-gh-widgets.service for 2026-07-21 shows the hourly timer failing on five of six runs, each identically:

RESOURCE_LIMITS_EXCEEDED  path: user.contributionsCollection.contributionCalendar.weeks
07:06 FAIL   08:06 FAIL   09:06 FAIL   10:08 FAIL   11:08 ok   12:10 FAIL

The single 11:08 success is the only reason a current SVG exists on disk. Commit 5d66691 already split the calendar into its own request and added transient-error retries; the retries are now exhausting. Splitting the query further is not a fix — the calendar-only query alone exceeds the node limit. The failing path is the calendar, not the PR or issue queries.

Separately, render.py holds no state of any kind: a grep for cache/state handling returns only unrelated matches. Every run pays full price for a year of history that cannot change.

02

Assumed vs. verified

Three assumptions were tested against the live API before this design settled. Two failed.

Assumed
  • CLOSED is a terminal state, so closed PRs and completed issues can be cached forever.
  • PRs can be windowed by date server-side, the same way the calendar can.
  • An "older than one week" rule can apply uniformly to calendar, PRs and issues.
Verified
  • Closed items reopen. IssueStateReason contains REOPENED; only MERGED is plausibly one-way.
  • The pullRequests connection takes only states, labels, headRefName, baseRefName, orderBy, first/last/after/before — no date argument exists.
  • contributionsCollection(from: DateTime, to: DateTime) does exist, so the age rule is correct for the calendar and only the calendar.
03

Change inventory

Every file the implementation touches, and the precise change.

render.py — new cache module
Add load/save of a JSON cache. Path from CACHE_FILE, defaulting to /var/lib/gh-widgets/cache.json. Schema-versioned, so a future shape change invalidates cleanly rather than mis-merging. A missing or unreadable cache is not an error — it degrades to a full fetch.
render.py — durability layer
Render from cache when a fetch fails. Any fetch raising after retries falls back to the cached values and renders normally, exiting 0. The rendered card carries the cache timestamp so staleness is visible rather than silent — a permanently-broken fetch must not present confident stale numbers.
render.py — fetch()
Window the calendar. Request contributionsCollection(from:, to:) for the trailing 7 days only, and merge those days onto the cached history keyed by date. Days older than 7 days are read from cache and never refetched.
render.py — fetch_pull_requests()
Split by state. Query states:[OPEN, CLOSED] live each run (a server-side filter, ~40 external items) and union with the cached MERGED set. A PR transitioning into MERGED is picked up because it appears in the live half until the run that first sees it merged, at which point it moves to the cached half.
render.py — --resync flag
Full rebuild, weekly. Discards the cache and refetches everything, so no correctness claim rests permanently on the assumption that MERGED is one-way. Wired as a second systemd timer, or a day-of-week check in the existing unit.
test_render.py
Cover merge and fallback. Cases: cached-day merge produces the same calendar as a full fetch; a fetch failure renders from cache and exits 0; a PR moving OPEN → MERGED is counted exactly once; a corrupt cache falls back to full fetch. Stdlib unittest, no network, matching the existing suite.
render-gh-widgets.service
Grant a state directory. Add StateDirectory=gh-widgets so /var/lib/gh-widgets exists with correct ownership, and set CACHE_FILE alongside the existing environment block.
04

What is cacheable, and why

Counts are live figures for this profile, external contributions only, taken with the widget's own token.

DataCountCacheableWhy
Calendar days older than 7d~358Yes — permanentlyA past day's contribution count cannot change.
Calendar days within 7d7NoToday's count still moves; the window is cheap.
PRs — MERGED192Yes, with weekly resyncMerge is believed one-way; the resync removes the need to be sure.
PRs — CLOSED21NoReopenable, and a reopened PR can still merge.
PRs — OPEN19NoThe mutable set by definition.
Issues — all states66NoREOPENED exists; accepted is defined as CLOSED+COMPLETED, so it can flip back. One page, not worth the risk.

Net effect per hourly run: a full year of calendar plus every PR and issue becomes 7 days of calendar, ~1 page of PRs, 1 page of issues. The external total must remain 232 opened / 192 merged — the figures the live SVG carried before this change.

05

Verification

Concrete and runnable. The parity check is the one that matters: the numbers must not move.

Unit suite passes. cd /root/gh-widgets && python3 -m unittest discover — stdlib only, no network.
Cold-cache parity. Render to a scratch OUT_DIR with no cache file; external widget shows 232 opened / 192 merged, matching the pre-change SVG.
Warm-cache parity. Render again against the populated cache; byte-identical SVGs to the cold run, apart from the timestamp.
Failure fallback. Point GH_TOKEN_FILE at an invalid token; the run exits 0, renders from cache, and the card shows the cache age.
Query size. The calendar request covers 7 days, confirmed by logging the from/to arguments — the run must not reproduce RESOURCE_LIMITS_EXCEEDED.
Deploy discipline. install -m 755 render.py /usr/local/bin/render-gh-widgets.py, then diff the two — deployment is a copied file under a different name, and repo/production have drifted silently before.
Live timer green. After deploy, two consecutive scheduled runs succeed in journalctl -u render-gh-widgets.service.

Risks

Risk
Sev
Mitigation
MERGED is not actually one-way, so an unmerged PR stays counted. Two GitHub doc pages failed to confirm reopen semantics (one silent, one 404); this is unverified.
MED
The weekly --resync rebuilds from scratch, bounding any drift to seven days instead of forever. The design deliberately does not depend on the assumption.
Durability layer masks a permanently broken fetch — widgets show confident but frozen numbers.
MED
The cache timestamp is rendered on the card, so staleness is visible to any viewer rather than silent.
Cache file corrupted or partially written, producing wrong totals.
LOW
Write to a temp file and rename atomically; a schema version guards shape changes; an unreadable cache degrades to a full fetch rather than failing.
Repo and production drift again — the deployed copy diverging from render.py.
LOW
Explicit diff step in the verification checklist, before and after deploy.
07

Out of scope

Considered and deliberately excluded.

Caching issue outcomes
Ruled out on evidence, not effort: REOPENED in the schema means no issue outcome is safe to freeze, and 66 items is already a single page. Revisit only if issue volume grows enough to matter.
Caching repository, star and language data
The stats and languages widgets query repositories(isFork: false), which is not the failing path and is small. Out of scope until it demonstrably costs something.
