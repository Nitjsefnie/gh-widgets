# :bar_chart: gh-widgets
### GitHub stat SVGs that render on a timer, not on every page load

`github-readme-stats` and friends render on *request* — someone opens your README, a box somewhere calls the GitHub API with your token. gh-widgets inverts it: a systemd timer renders SVG files to disk, nginx serves them as files. No runtime API calls, no JS, no third party holding a token, no rate limit tied to how many people view your profile.

Real files off my own account, regenerated hourly. Hotlink one into a README and it just works — it's an image.

## :chart_with_upwards_trend: The five widgets
`stats`, `streak` and `languages` are the usual profile cards. The two I built this for are about *other people's* repos:

**external** — 306 PRs opened, 263 merged, across 73 repos · 109 issues, 76 maintainer-accepted, across 49 · **86% merged · 70% maintainer-accepted**.
**impact** — below. It's the interesting one.

## impact.svg — share, not volume
Contribution graphs reward noise. `impact.svg` asks a harder question: *of the work in this repo, how much is mine?* Three ranked tables — Pull Requests, Issues, and **Live Code** — each scored `WilsonLowerBound(mine/total, z) * mine^gamma`, so a 1-of-1 repo can't outrank a sustained relationship.

Live Code means what it says: `git clone` each candidate repo (full history — blame needs it), blame it, count the lines still surviving under my authorship, delete the clone. Top row: **2,749 of 11.3k lines in `envaar/vaar` — 24.3%**. Top PR row: 24 of 64 in `warior456/Sculk-Depths`, 37.5%.

## :tools: Stack
Python **3.9+**, **stdlib only** — no `requirements.txt`, nothing to install. GraphQL throughout. One exception: `render-impact.py` shells out to `git` and `git-fame` for the blame pass.

```
┌──────────────┬─────────────────────┬──────────────────┐
│              │ github-readme-stats │   gh-widgets     │
│              │                     │   (this repo)    │
├──────────────┼─────────────────────┼──────────────────┤
│ Render       │ per request         │ systemd timer    │
│ Serving      │ hosted service      │ static files     │
│ Your token   │ on their box        │ on yours         │
│ Deps         │ Node + npm tree     │ Python stdlib    │

│              │                     │   landed in      │
└──────────────┴─────────────────────┴──────────────────┘
```

:robot: Most of the code in the repos `impact.svg` measures was written by agents, and gh-widgets is the thing that keeps score. Turtles most of the way down.

## :zap: Follow-up: why "live code" is expensive, and how it stays cheap

Counting *surviving* lines is the only honest way to measure code impact — added-lines counters reward a big commit that someone deleted the next week. But it means blaming whole repositories, which is not something you can do on a timer without thinking about it.

What keeps it affordable:

```
candidate set     only repos where a PR of mine actually merged
clone depth       full history (blame is wrong without it)
re-blame trigger  default-branch HEAD oid changed since last count
otherwise         reuse the cached line count, clone nothing
disk              clone → blame → delete, one repo at a time
schedule          twice daily (05:30 / 17:30 UTC), after the hourly pair
```

So a normal run blames nothing at all — it checks HEAD oids and reuses counts. Only a repo that actually moved pays for a clone, and only `--resync` re-blames everything at once.

```
cache.json          252 KB   366 calendar days, 1,098 PRs
impact-cache.json   264 KB   PRs, issues, totals, per-repo line counts
```

Two caches, deliberately separate — pointing both renderers at one file was a mistake I made once and would rather nobody repeat.

Two more things that keep a scheduled renderer from lying to you quietly:

:gear: **The three Python files ship as a matched set.** Each renderer asserts the shared module's `COMMON_VERSION` at startup and hard-exits on mismatch, so a half-finished `cp` gives you a renderer that refuses to run instead of one that quietly renders from a stale module.

:shield: **Fail-soft, in the right direction.** A corrupt or schema-mismatched cache falls back to a full fetch; a failed live fetch with a good cache renders from cache and *shows you the cache timestamp* rather than breaking the image. A stat widget that silently serves stale numbers is worse than one that visibly does.

:calendar: And the reason a full-year contribution query isn't one query: GitHub answers it with `RESOURCE_LIMITS_EXCEEDED`. A cold cache walks 12 sequential monthly windows; a warm one refetches only the trailing 7 days and merges onto the cached ones.
